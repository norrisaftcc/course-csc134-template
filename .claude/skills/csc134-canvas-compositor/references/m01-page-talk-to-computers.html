Module 01 · Reading

Talk to Computers (and Your Team)

You will not write any C++ this week. First you need a way to write things down that a computer, a teammate, and an AI can all read without arguing about it. That format is plain text. This page gets you set up to use it.

Every file you turn in this term is a plain text file. Your programs are plain text. Your notes are plain text. Your flowcharts, later on, are plain text that gets drawn into a picture. This is not a rule I made up to be difficult. It is the reason two people can work on the same program at the same time and see exactly what changed.

Why not Word?

A Word document is not text. It is a zip file full of formatting instructions with your words buried inside. A compiler opening it sees garbage. So this term you use VS Code, which is an editor for text and nothing else. It looks plainer than Word because it is doing less, on purpose.

Caution

Do not draft code in Word or Google Docs and paste it over. Both of them silently change straight quotes (") into curly quotes (“), and a compiler will not accept a curly quote. This is one of the most common ways a first program fails for a reason that has nothing to do with programming.

The markup ladder

Plain text on its own has no headings, no bold, no links. People fixed that three times, each fix a step up from the last:

  1. .txt — just characters. Universal, and completely unstructured.
  2. .md — Markdown. A few punctuation marks stand for structure. A # is a heading; a - is a bullet. Still readable if nothing renders it.
  3. .html — every piece of structure spelled out in tags. Total control, much more typing, unpleasant to read raw.

Markdown is the middle rung, and the middle rung is where the work happens. It is structured enough to be useful and plain enough that you can read it with no tools at all.

Note

Markdown was a small niche format for about a decade. Then chat-based AI tools arrived, and every one of them reads and writes Markdown by default, because it carries structure in characters a language model already handles well. Learning it is no longer just a submission requirement. It is how you talk to those tools.

Here is a whole Markdown file. That is all there is to it:

# CSC 134 — Alex Rivera

My repository for C++ Programming.

## What is in here

- `module-00/` — setup and first program
- `module-01/` — this README, and the sandwich

I am using **Codespaces**, not a local install.

Four kinds of structure in nine lines: two headings, a list, bold text, and code formatting on the folder names. You already know enough Markdown to write your own.

How your work gets to me

You do not email me files and I do not download attachments. Your repository on GitHub is the submission. Four moves, in this order, every time you sit down to work:

Participants: You · Your computer · GitHub

01  GitHub → Your computer

Pull. Bring down anything that changed since last time — new starter files from me, or your own work from a different machine. Do this before you edit anything.

02  You → Your computer

Edit and save. Normal work. Nothing has been recorded yet; saving a file is not a submission.

03  You → Your computer

Commit. Take a snapshot and write one line saying what changed. Add sandwich steps 1–6 is a commit message. stuff is not.

04  Your computer → GitHub

Push. Send your commits up. Now it exists somewhere other than your laptop, and now I can see it.

Skipping step 01 is what causes the first error most people hit. If you edit on GitHub's website and then push from your computer, the two disagree and GitHub refuses the push:

 ! [rejected]        main -> main (fetch first)
error: failed to push some refs
hint: Updates were rejected because the remote
hint: contains work that you do not have locally.

Nothing is broken and nothing is lost. It is telling you to pull first, then push again. You will see this message several times this term, and after the second time it stops being alarming.

Instructor · out of character

Setup week is the week people quietly decide they are not cut out for this. Fighting an account, a permission, or a piece of software is not a measure of whether you can program — it is a measure of how many undocumented steps someone left out. If you lose more than half an hour to setup, stop and message me or come to office hours. I would much rather unstick you in five minutes than have you spend the weekend on it.

Before you move on

Setup checklist

  • I have a GitHub account, and I have sent my username in.
  • I can open my course repository and see a list of files in it.
  • I know which setup I am using this term — Codespaces in a browser, or VS Code installed on my own machine.
  • My README.md has my name, at least one heading, and at least one list.
  • I have pushed at least one commit, and I can see my own words on the GitHub website in a browser.
