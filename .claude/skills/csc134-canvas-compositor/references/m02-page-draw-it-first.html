Module 02 · Reading

A flowchart is a drawing of a decision. From here to the capstone you will draw one before you write the code, so this page covers the four shapes, one worked example with no programming in it at all, and the trick that makes a flowchart something you can keep in your repository instead of on a napkin.

Why draw first

"Bring an umbrella if it looks like rain" is a perfectly good sentence and a useless instruction. Looks like rain to whom? What if it is dry now and pouring by five? A person fills those gaps without noticing. A computer cannot fill them at all, and neither can an AI — it will just guess confidently.

Drawing the decision forces you to say what happens in every case, because an unfinished branch is visibly unfinished. An arrow that goes nowhere is obvious on paper. The same gap buried in thirty lines of code is not.

Four shapes

  • Rounded box — where the process starts or stops.
  • Rectangle — do something. One action per box.
  • Diamond — ask a question with a yes-or-no answer. Two arrows leave it, labelled.
  • Arrow — what happens next. Arrows carry the order; the boxes only carry the work.

That is the entire notation. The diamond is the one that matters this term, because a diamond is exactly what an if statement is going to be in two modules' time.

A flowchart with no code in it

Here is the umbrella problem, decided properly. Read the spine down the left; each question sends you sideways or sends you further down.

In words: check the weather, then ask whether it is raining right now. If it is, take the umbrella and you are done. If it is not, ask whether rain is forecast. If it is, take a jacket and you are done. If it is not, take nothing. Three ways out, and every question has both of its answers accounted for. That last part is the whole discipline.

Notice the shape: each yes hangs off to the right and ends there, while the no path continues straight down. That is not decoration. It is what a chain of decisions looks like when the strictest question comes first, and it is the shape your gatekeeper program will have in Module 4.

Now the same diagram, written as text:

```mermaid
flowchart TD
    A([Check the weather]) --> B{Raining now?}
    B -- yes --> C[Take umbrella]
    B -- no --> D{Rain in forecast?}
    D -- yes --> E[Take a jacket]
    D -- no --> F[Take nothing]
```

Six lines of text, and they mean the same thing as the picture above. Round brackets make a rounded box, square brackets a rectangle, curly braces a diamond, and --> is an arrow. The words after the dashes are the branch labels. This is called Mermaid, and it is the reason your flowcharts are going to live in your repository next to your code: put that block in a .md file, push it, and GitHub draws the picture for you.

Which means a diagram is code. It gets committed, it shows up in a diff when you change it, and it can never be lost in a bag or left on a whiteboard. Every plan you hand in this term is a Mermaid block.

Pseudocode: the same plan in sentences

A flowchart is good at showing shape and bad at holding detail. Pseudocode is the opposite: plain sentences, indented to show what belongs inside what, with no attention paid to any real language's punctuation.

check the weather

if it is raining now
    take the umbrella
else if rain is in the forecast
    take a jacket
else
    take nothing

No semicolons, no braces, nothing to compile. And yet the indentation is already doing the job that curly braces will do in C++, and if / else if / else are already in the right order. Use the flowchart to find the shape, then the pseudocode to pin down the detail, then write the code. Three passes, each one cheaper to fix than the next.

Before you move on

  • I can name what each of the four shapes is for without looking.
  • I typed a Mermaid block into a .md file, pushed it, and saw GitHub draw it.
  • Every diamond in my own flowchart has two labelled arrows leaving it — I checked each one.
  • I can point at one line of my pseudocode and say which box in my flowchart it came from.

Instructor · out of character

People skip the drawing because it feels like the part that isn't real work. I skipped it for years. What changed my mind was counting how long I spent fixing programs whose logic I had never actually decided — the drawing takes four minutes and it is the cheapest debugging you will ever do. If you try it for two assignments and it genuinely doesn't help you, tell me and we'll talk about it. Just try it twice first.
