Write a program that puts someone in the player's way, checks two things about them, and then picks exactly one ending out of several — based on what the user typed.

In the Apply tutorial you typed in the Gatekeeper: a scene where a character looks you over, asks a question or two, and then decides what happens to you. Now you write your own. Same input, same ending, every time. Different input, different ending. That is what decisions do — they make the program fork.

The Gatekeeper is one skin, and you do not have to keep it. A nightclub bouncer checking your ID and the guest list. An airport gate agent checking your ticket class and your bag weight. A loan officer checking your account type and your credit score. Pick whatever scene you like — the decisions underneath are the same, and the decisions are what you are graded on.

The specification

This is the contract. Read it with the theme words removed and it still tells you exactly what to build.

Inputs, typed by the user, in this order

  1. A category — a whole number 1, 2, or 3 that picks who or what kind. Warrior/Mage/Rogue, or Merchant/Pilgrim/Smuggler, or Standard/Business/First — your call.
  2. A score — a whole number from 0 to 100 that the program compares against thresholds.
  3. Higher tiers only. One more small input — a yes/no answer (1 or 0) that only some categories are asked for.

Processing

  1. A switch on the category prints a category-specific line. A category number the switch does not recognize lands in the default case, which prints a "you don't belong here" line and ends the program cleanly. That default is a designed ending, not a crash.
  2. An if / else if / else chain with at least three branches compares the score against thresholds and picks the outcome. Order the branches from the highest bar down to the lowest, so each else-if only runs when the ones above it were false. The threshold values are yours to choose — they need not match the example numbers used here. The only rule is highest bar first.

Outputs

The category line, then the outcome line or lines. Every run ends with exactly one outcome. No run falls off the end having printed nothing.

Here is a C-tier run in the Gatekeeper skin, where the score clears the top bar:

A gatekeeper blocks the door. She looks you over.
Your class? (1 = Warrior, 2 = Mage, 3 = Rogue): 1
"A Warrior. Strong arms, I hope."
Your strength score (0-100): 85
The gate swings wide. "Strong enough. Go through."
The visit ends.

And here is the same program taking the designed exit, because 7 is not a category it knows. Notice it ends deliberately, with a sentence, rather than falling over:

A gatekeeper blocks the door. She looks you over.
Your class? (1 = Warrior, 2 = Mage, 3 = Rogue): 7
"I do not know that class. Off you go."
The gate stays shut.

The spec above is the whole target. The scene words are yours to change; the switch, the three-branch chain, and the graceful default are not.

How far you take it

Two separate things are scored: which tier you attempt, and how the attempt scores across four columns. Tiers nest — B includes all of C, A includes all of B. You earn the highest tier at which all four columns pass.

You can stop at C with a complete, working, submittable program. C is the objective met, not partial credit.

C
core		 A Mermaid flowchart drawn first, then a program using a switch (3+ cases plus a graceful default) on the category and an if / else if / else chain (3+ branches) on the score, with every branch reachable, matching the flowchart, compiling clean.
B
depth		 Everything in C, plus one compound condition (&&, ||, !) that changes an outcome, and one single-pass out-of-range input check that rejects and ends cleanly. No loop.
A
synthesis		 Everything in B, plus a branching tree with four or more distinct outcome messages (distinct means different printed text), each printing for a different combination of category and score, and at least one genuinely nested condition — an if inside a branch, not just another else-if.
Badge
above & beyond		 A recovered flowchart for the snippet below (code → flowchart, the reverse direction), a complete prompts.md if AI was used, and a 3-5 sentence reflection. Badge is documentation, never more code, and never rescues a failed column.

C tier — the core scene

  1. A flowchart in m4lab-plan.md, drawn as a Mermaid diagram, matching your finished code.
  2. A switch on the category input with at least three cases plus a default that ends the program gracefully.
  3. An if / else if / else chain with at least three branches on the score — a high case, a middle case, a low case.
  4. Every branch is reachable, and every run prints exactly one outcome.
  5. Compiles clean under the course build command — zero warnings.

B tier — depth

  1. One compound condition using &&, ||, or ! that actually changes an outcome. For example, a middle-score result that only happens when the score is in range and a yes/no answer was yes.
  2. One single-pass input check that rejects an out-of-range score with a clear message and ends cleanly. This is one check, not a loop. Looping until the input is valid is an M5 move — do not use a loop here. A single if that rejects and stops is exactly right.

A tier — synthesis

  1. A real branching tree with four or more distinct outcome messages, each printing for a different combination of category and score. Distinct means different printed text — four separate messages, not the same line reached four ways.
  2. At least one genuinely nested condition — an if inside another branch's body, not just another link in the else-if chain.

Badge — documentation, not more code

  1. A recovered flowchart. In m4lab-plan.md, under a heading "Reverse Recovery," draw the Mermaid flowchart for the snippet below — read the code, recover the diagram.
  2. prompts.md — if you used AI at all, list every prompt you sent and one sentence each on what you changed or rejected about the answer.
  3. A short reflection, 3-5 sentences, naming where you used && versus || (or why you used neither) and what would break if you swapped one for the other.

The snippet to recover a flowchart from:

int temp = 0;
cin >> temp;
if (temp >= 100)
    cout << "Boiling.\n";
else if (temp <= 0)
    cout << "Freezing.\n";
else
    cout << "Liquid.\n";

How it is scored

No hidden criteria — what is on this page is the whole rubric. You choose a tier; you are scored on the four columns below.

Correctness · 8

Every branch prints the ending your flowchart says it should, for the inputs listed under Testing. The default ends cleanly on an unknown category, and the boundary values — 70 against 69, say — land in the right branch. At B, the compound condition changes the outcome it claims to, and the out-of-range check rejects rather than running a normal branch. Any remaining defect is logic-level and named in m4lab-plan.md.

Completeness · 6

Everything the attempted tier lists is present, and the flowchart and the code tell the same story.

Format · 3

Compiles clean with zero warnings. Everything in main — no functions, no prototypes, no loops. Variables named for what they hold. Every branch body braced. The Mermaid diagram renders on GitHub.

Submission · 3

m4lab.cpp and m4lab-plan.md in the correct folder, committed and pushed directly to your repo — no branches. prompts.md present if you used AI. If it is not visible on github.com, it is not submitted.

Caution

Most students who lose points on this lab lose them to a warning, not a broken program. One warning means Format is not met, at any tier — so an A-tier feature set that builds with a warning does not score as A. Fix the warning and the whole thing counts. This is a fix-and-resubmit conversation, not a penalty one.

Building it

There is no starter file. You type the whole thing in yourself, from the spec, the same way you typed in the Gatekeeper — that is the point of this stage. Build it up in small pieces and compile often. Do not write the whole program and compile once at the end.

A good build order: print the opening line and compile. Add the category read and the switch with its default, then try a bad category and confirm the default ends it. Add the score read and the three-branch chain, running each branch. Then, if you are going further, add the compound condition and the single-pass check (B), and the nested condition and extra outcome messages (A).

Create your file, then build and run with the course-standard command:

g++ -std=c++17 -Wall -Wextra -o m4lab m4lab.cpp
./m4lab

Single-file rules for this module: everything lives inside main. No functions, no prototypes — those arrive in M6. No loops — those arrive in M5. This lab is if / else if / else, switch, and logical operators only.

Before you submit

Pre-flight

  • I ran git pull before starting this checklist.
  • My build printed zero warnings, not just zero errors. I read the output rather than assuming.
  • I ran each valid category (1, 2, 3) and at least one the switch does not define (0, 4, or 9), and the undefined one ended cleanly.
  • I tested my exact threshold numbers and the value just below each one. Off-by-one at a boundary is the most common Logic error here.
  • I tested a score of 0 and it reached a real ending, not an out-of-range rejection.
  • Every branch body has braces around it, and every case has a break.
  • My flowchart in m4lab-plan.md matches the code I actually wrote, and it renders on github.com.
  • Both files are in the m4/ folder, committed and pushed.
  • I opened my repo on github.com and saw both files there. If I cannot see them, neither can my instructor.

Going for the Badge? Add prompts.md to the same commit, with every AI prompt you used and what you changed about the answers.
