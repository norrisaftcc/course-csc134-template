Module 04 · Reading 3 of 3

Three classic decision bugs. This course does not spring traps on you as gotchas — we name them here, out loud, so that when one bites in lab you recognize it instead of losing an afternoon.

All three are Logic errors: the program did exactly what you said, not what you meant. That is what makes them worth naming. A Syntax error stops you at the door and tells you so. These let you all the way in and then quietly hand you the wrong answer.

Trap 1: one equals sign instead of two

One equals sign assigns. Two equals signs compare. Inside an if, you almost always want two.

if (strength = 70)   // BUG: this ASSIGNS 70 to strength, then the if is "true"

That line sets strength to 70 and then treats the result as true — so the branch runs every time, no matter what the player typed. The good news is that the compiler is watching. Under our build flags it prints suggest parentheses around assignment used as truth value [-Wparentheses] and even suggests the fix. That warning is exactly why this course compiles with -Wall -Wextra and demands zero warnings. Memory hook: one equals gives, two equals asks.

Trap 2: switch fall-through

Every case needs its own break;. Forget it, and the program keeps running straight into the next case.

switch (characterClass)
{
    case 1:
        cout << "\"A Warrior.\"\n";
        // BUG: no break here!
    case 2:
        cout << "\"A Mage.\"\n";
        break;
    ...
}

Predict first. The player is class 1 — a Warrior. What prints? Decide before you read on.

"A Warrior."
"A Mage."

Both. With no break after case 1, control "falls through" into case 2 and runs it too. One player, two identities, no complaint from anybody.

Caution

This is the most dangerous of the three, and the reason is what the compiler does not say. On our compiler this produces no warning at all — it compiles clean and just does the wrong thing quietly. There is no red text to save you here; only your own testing will. Put a break; at the end of every case.

Trap 3: the dangling else

Without braces, an else pairs with the nearest if — not the one your indentation seems to point at.

if (strength >= 40)
    if (hasLockpick)
        cout << "Clever hands.\n";
else                              // looks like it pairs with the OUTER if...
    cout << "Turned away.\n";     // ...but it actually pairs with the INNER if

The indentation suggests the else belongs to the strength check. It does not. It binds to the lockpick check, the closest one. So a strong player without a lockpick prints "Turned away." — the opposite of what the layout implied. The indentation was a lie, and C++ never read it.

Pro tip

Braces on every if, else if, and else — always, even for a single line. It kills Trap 3 outright and makes Trap 1 easier to spot. It is the cheapest good habit in the module.

Putting it together

You now have the whole M4 toolkit. An if / else if / else chain for ranges and thresholds, checked top to bottom and stopping at the first true branch. A switch with a default for matching one number against exact choices. Comparison operators to build a single condition, and && || ! to combine them. Nesting, to ask a follow-up question only when it makes sense. And three named traps that all show up as Logic errors.

That is exactly the gatekeeper. And the gatekeeper is exactly the diamond you have been drawing since M2 — now executable.

Common questions

"What if the user types a letter where I asked for a number?"

Input reading stops and the variable keeps its old value — the stream enters a "fail state." That is a Runtime failure: the program ran, then fell over. M4 programs assume you typed a number; M5 is where you learn to loop until the input is valid. For now, test with good input and name the failure when you see it.

"When do I use switch instead of else if?"

Use switch when you are comparing one variable against a list of exact whole-number values — a menu, a class code. Use else if for ranges, and for conditions that mix different variables. You cannot switch on "70 or more"; a range is not an exact value.

"Do I have to memorize all this syntax?"

The shapes, yes — you will type them enough that they stick. The exact operator list, no; keep the tables from Readings 1 and 2 open while you work. Reading fluency matters more than recall.

"Can I just ask AI to write the branches?"

For explaining a branch you are stuck on, yes — that is a fine use of the AI ladder. But you will be graded on whether you can trace which branch runs and read the flowchart against the code. You cannot supervise code you cannot read, and Assess will ask you to read it. If you use AI, record it in your prompts file.

Check yourself

1. Trace it. In the Reading 1 program, the player types 40. What prints?

Answer

Borderline. Answer my riddle and the gate is yours. — 40 is not 70 or more, but 40 is 40 or more, because the operator includes the number itself. So the middle branch runs.

2. Classify the error. A student writes a condition that assigns instead of compares. It compiles, with a warning, and the branch runs every single time. Which of the four error types is this — Syntax, Static semantic, Runtime, or Logic?

Answer

Logic. It compiled and it ran. It just did what was written — assign, always true — instead of what was meant. The warning is the compiler trying to save you from a Logic bug, which is a favour it does not usually do.

3. Recover the flowchart. Read the switch from Reading 2 and sketch its flowchart on paper: one entry, one diamond per class, and where default goes. This "code back to a diagram" move is graded later in the module, so practise it now.

One valid shape, written as Mermaid — the notation you will be writing yourself:

flowchart TD
    A([Read class]) --> B{class == 1?}
    B -- yes --> W["A Warrior"]
    B -- no --> C{class == 2?}
    C -- yes --> M["A Mage"]
    C -- no --> D{class == 3?}
    D -- yes --> R["A Rogue"]
    D -- no --> X["default: unknown class"]

A switch is really a stack of exact-match diamonds, with default as the final "none of these" exit. Seeing it drawn that way is also the clearest argument for always giving one.
