Module 04 · Reading 1 of 3

Every program you have written so far runs the same way no matter what the user types. This is where that changes — where the diamonds you have been drawing since M2 become code that actually forks.

By the end of this page you will be able to trace which branch of an if / else if / else chain runs for a given input, build a condition out of comparison operators, and read a decision flowchart against the code that came from it.

Why this matters

In M3, every program was one straight path from the top of main to the bottom. Read some input, do some math, print the result. Useful, but a little dumb — the program never chose anything.

This is also where the course starts talking about filters: conditionally processing input, letting some values through and turning others away. That idea runs all the way up to your capstone, and you will meet it again in every language you touch in a four-year program. The keywords change; the fork does not.

Our running scene is a dungeon gatekeeper. She stands at a door, sizes you up, and decides whether you get through — a filter with a story wrapped around it. The scene reskins cleanly: a nightclub bouncer checking IDs, a loan officer reading an application, an airport gate agent. The decisions stay exactly the same. If you swap the story and the logic breaks, the story was welded on too tight. It should peel off like a sticker.

One fork: if / else

The simplest decision does one thing when a condition is true and another when it is false.

if (strength >= 70)
{
    cout << "The gate swings wide.\n";
}
else
{
    cout << "Turned away.\n";
}

The thing in the parentheses is a condition — an expression that is either true or false. If it is true, the first block runs. Otherwise the else block runs. Exactly one of them runs, never both.

The gatekeeper measures you: if / else if / else

Two outcomes are rarely enough. The gatekeeper has three answers ready — pass, maybe, and no — depending on how strong you are. You chain the checks with else if.

Predict first. Read this complete program. If the player types 55, what prints? Decide your answer before you read past the program — the whole skill this module builds is being able to say what a branch will do before you run it.

#include <iostream>
using namespace std;

int main()
{
    int strength = 0;                 // a whole number, 0 to 100
    cout << "Your strength score (0-100): ";
    cin >> strength;

    if (strength >= 70)
    {
        cout << "The gate swings wide. Go through.\n";
    }
    else if (strength >= 40)
    {
        cout << "Borderline. Answer my riddle and the gate is yours.\n";
    }
    else
    {
        cout << "Too weak. Turned away.\n";
    }

    return 0;
}

Have your answer? Read on.

Typing 55 prints: Borderline. Answer my riddle and the gate is yours.

Here is the part people miss. 55 is greater than or equal to 40 — but it is also checked against 70 first, and that check was false. So we fell through to the second test. A chain is checked top to bottom, and it stops at the first true branch. Put the 40 check first instead, and a score of 70 would match it before the 70 check ever got a look. That branch would become unreachable — a Logic error: the program did what you said, not what you meant.

Comparison operators

The condition is built from comparisons. These six are your whole toolkit in M4.

> greater than — gold > 50
< less than — health < 20
>= greater than or equal — strength >= 70
<= less than or equal — enemies <= 3
== equal to — two equals signs — characterClass == 3
!= not equal to — answer != 0

Caution

Most students who lose an afternoon in this module lose it to a single equals sign. One equals assigns; two equals compare. Inside an if, you almost always want two. Memory hook: one equals gives, two equals asks.

A decision, drawn

Here is that same strength chain as a flowchart — the diamonds you have been drawing since M2, now backing real code. Read it top to bottom and match each fork to an else if in the program above.

      ┌──────────────┐
      │ Read         │
      │ strength     │
      └──────┬───────┘
      ┌──────┴───────┐
      │ strength     │
      │ >= 70 ?      │
      └──┬────────┬──┘
     yes │        │ no
  ┌──────┴─────┐  │
  │ Gate opens │  │
  └────────────┘  │
       ┌──────────┴───┐
       │ strength     │
       │ >= 40 ?      │
       └──┬────────┬──┘
      yes │        │ no
  ┌───────┴────┐   │
  │ Riddle     │   │
  └────────────┘   │
           ┌───────┴──────┐
           │ Turned away  │
           └──────────────┘

In words, because a picture made of line characters is not much use to a screen reader and not much use on a phone either: the program reads a strength score. If it is 70 or more, the gate opens and the visit ends. Otherwise it asks a second question — is the score 40 or more? If yes, the player gets a riddle and a half-open gate. If no, they are turned away. Each fork has exactly two exits, and every path ends.

That diagram is not a picture someone drew for you — it is written, in a notation called Mermaid, and it renders on GitHub. This is the source that produced the shape above, and it is the notation you will write yourself in the Apply tutorial and be graded on in the lab:

flowchart TD
    A([Read strength]) --> B{strength >= 70?}
    B -- yes --> C[Gate swings wide]
    B -- no --> D{strength >= 40?}
    D -- yes --> E[Borderline: a riddle]
    D -- no --> F[Too weak: turned away]
    C --> G([Visit ends])
    E --> G
    F --> G

A diamond is a decision, a rounded box is a start or an end, and an arrow labelled yes or no is a branch. Notice that the drawing and the code say the same thing twice, in two notations — and that one of those notations is plain text you can type. In Apply you will draw one of these before typing any code. In Assess you are graded on whether your flowchart and your code tell the same story.
